# AI 智能试衣间｜项目开发大纲（全生命周期）

> 适用范围：本仓库（`web/` + `api/`）所对应的“AI 智能试衣间”项目，从立项到上线与验收的全流程指导文档。

## 1. 项目背景与目标

### 1.1 项目背景

本项目为前后端分离的 AI 试衣间 MVP，核心链路为：

1. 用户上传照片与体型参数
2. 生成“数字人/形象图”
3. 选择姿态（pose）
4. 选择衣橱单品
5. 一键试穿生成结果图并可预览/保存

推理侧支持对接 Gemini 图像生成能力（`gemini-2.5-flash-image`），并将生成结果落盘到后端静态目录 `/static/*` 供前端访问。

### 1.2 业务目标

- **闭环目标**：用户在 3 分钟内完成“上传 → 生成 → 试穿出图”的完整流程
- **体验目标**：生成过程可观测（进度/阶段/错误信息明确），失败可重试
- **扩展目标**：推理 Provider 可插拔（Gemini 优先，后续可扩展其它服务）

### 1.3 技术目标

- 前后端解耦与可独立部署
- 推理调用具备超时、错误处理与降级路径
- 资产与生成结果可持久化、可追溯
- 线上可观测、可回滚、密钥不入库

## 2. 项目范围、非目标与关键假设

### 2.1 Scope（项目范围）

- 数字人生成：`avatar_generate`
- 姿态渲染：`pose_render`
- 虚拟试穿：`vton_tryon`
- 资产上传：`POST /v1/assets/upload`
- 结果访问：`/static/*`（图片可通过 URL 被前端直接加载）
- 任务接口：创建任务、查询任务、进度事件（轮询/可扩展 SSE）

### 2.2 Out of Scope（非目标）

- 电商域：SKU/库存/支付/订单履约等复杂能力（可保留页面/接口占位，不作为一期交付）
- 多租户企业权限、审计、复杂 RBAC（可作为二期演进）
- 复杂推荐/穿搭算法（可在二期以策略服务方式接入）

### 2.3 关键假设与约束

- 所有密钥通过环境变量注入，不写入仓库
- 单次推理时延满足业务可接受范围（超时需给出可解释反馈）
- 线上需要配额/限流策略，避免成本失控

## 3. 核心功能模块

### 3.1 前端（`web/`：Next.js）

- 门户页与工作台：入口导航、流程引导
- 数字人生成页：上传照片、体型参数校验、任务进度展示、结果保存为“当前数字人”
- 衣橱页：上传单品、单品列表（供试穿选择）
- 工作室页：姿态切换、单品选择、一键试穿、结果预览、错误提示与重试

### 3.2 后端（`api/`：FastAPI）

- 资产服务：文件校验、上传落盘、静态资源服务（`/static/*`）
- 任务服务：任务创建、任务查询、进度上报、失败与错误结构化返回
- 推理适配层：
  - Gemini（`generateContent`）模式：通过 `NANOBANANA_API_KEY` + `NANOBANANA_MODEL` 调用并落盘输出
  - 远程 Endpoint 模式：通过 `NANOBANANA_API_KEY` + `NANOBANANA_ENDPOINT` 调用自建/封装服务
  - Mock 模式：在缺少关键配置时用于链路打通与本地开发

### 3.3 数据与存储

- MVP：本地文件存储（`api/storage/`）+ 内存任务存储（JobStore）
- 生产建议：
  - 对象存储（S3/R2/OSS）存放图片、掩码、JSON 结果
  - PostgreSQL 存储任务、用户、资产元数据
  - Redis 作为队列/缓存（异步任务与去重）

### 3.4 运维与可观测

- 日志（请求、任务、推理调用）
- 指标（成功率、失败率、p95 延迟、队列长度、配额/限流触发次数）
- 告警（推理异常激增、配额耗尽、服务不可用）
- 错误追踪（可选：Sentry/OTel）

## 4. 技术选型方案（含选型依据）

### 4.1 前端框架

- **Next.js（当前仓库已使用 Next 16）**
  - 选型依据：路由与页面组织成熟、生态完善、部署到 Vercel 成本低；利于后续引入 SSR/缓存策略
- **React（当前仓库已使用 React 19）**
  - 选型依据：组件生态丰富、开发效率高
- **状态管理：Zustand（当前已使用）**
  - 选型依据：轻量、学习成本低、适合 MVP 状态管理（avatar/closet/任务状态）
- **校验：Zod（当前已使用）**
  - 选型依据：表单与 API 参数校验一致性好，错误提示友好
- **样式：Tailwind（当前已使用）**
  - 选型依据：迭代速度快、可统一设计语言、便于快速交付

### 4.2 后端服务

- **FastAPI（当前已使用）**
  - 选型依据：高开发效率、良好类型系统、适合 I/O 密集（上传/下载、外部推理调用）
- **Uvicorn（当前已使用）**
  - 选型依据：轻量可靠、支持热重载，部署成熟
- **Pydantic v2（当前已使用）**
  - 选型依据：数据模型声明式、校验与序列化能力强
- **HTTPX（当前已使用）**
  - 选型依据：异步 HTTP 客户端，适合对接第三方推理与图片下载

### 4.3 数据库（生产建议）

- **PostgreSQL**
  - 选型依据：任务/资产/用户等结构化数据强一致性需求；便于统计分析与审计追踪

### 4.4 部署环境

- **推荐组合：Vercel（前端）+ Render（后端）**
  - 选型依据：前端静态/SSR 与 Vercel 匹配度高；后端以容器/服务方式部署成本低、运维简单
- **企业/生产增强：Docker + 云主机 / K8s**
  - 选型依据：统一网络与存储、可灰度、可观测性完善、易做权限隔离与扩容

### 4.5 推理模型与调用方式

- **Gemini 图像生成模型：`gemini-2.5-flash-image`**
  - 选型依据：支持通过 `generateContent` 同时输入图像与文本，并返回图像结果，适合“参考人像 + 参考服装”的试穿场景
  - 调用依据：Gemini 文档说明支持通过 `generateContent` 传入 `inline_data` 图片（base64）进行多模态请求（详见官方文档）。

## 5. 项目实施 Timeline（五阶段 + 里程碑）

> 阶段按“需求调研 → 设计 → 开发 → 测试 → 上线”划分，里程碑应在项目管理工具（Jira/飞书项目/Notion）固化。

### 5.1 需求调研阶段

- 里程碑：需求范围确认（Scope/Out of Scope）
- 里程碑：用户流程与关键指标确认（成功率、等待时延、转化）
- 里程碑：合规评审完成（用户照片处理、存储与删除）

### 5.2 设计阶段

- 里程碑：交互原型与信息架构确认（Avatar/Closet/Studio/Workbench）
- 里程碑：API 契约冻结（OpenAPI：上传/任务/查询/事件）
- 里程碑：推理提示词与质量门控方案评审（失败降级、超时、重试、成本约束）

### 5.3 开发阶段

- 里程碑：后端资产服务与静态访问完成（/static 可访问）
- 里程碑：任务系统可用（创建/查询/状态机完整）
- 里程碑：Gemini 推理链路跑通（多图输入、返回图落盘）
- 里程碑：前端主流程闭环（上传→生成→姿态→试穿→展示）

### 5.4 测试阶段

- 里程碑：单元测试/集成测试达标（见第 7 节）
- 里程碑：性能基线报告完成（并发、超时、失败率、成本估算）
- 里程碑：上线演练完成（密钥轮换、回滚、故障注入）

### 5.5 上线阶段

- 里程碑：生产环境部署完成（域名、HTTPS、环境变量、跨域）
- 里程碑：监控告警生效（错误率、延迟、第三方失败率、配额）

## 6. 资源配置规划

### 6.1 人员配置（建议最小配置）

- 产品/项目负责人：需求、验收、里程碑推进
- 前端工程师：页面与交互、状态管理、性能优化
- 后端工程师：API、任务系统、存储、部署与可观测
- 算法/提示词负责人：提示词迭代、质量评估、回归集维护
- QA/测试：用例设计、自动化测试、上线演练与验收支持

### 6.2 环境与权限

- dev/staging/prod 三套环境变量与密钥隔离
- Gemini Key 配额与权限分级（最小权限原则）
- Vercel/Render 账号权限分级（Owner/Developer/Viewer）

### 6.3 资源与容量规划（建议）

- 请求限流：按 IP/用户/Key 维度限流
- 任务并发：控制并行推理数，必要时排队
- 资产存储：设置存储 TTL（如 7/30 天）与清理策略

## 7. 质量保障体系（覆盖率要求）

### 7.1 单元测试（Unit Test）

- 覆盖率要求：**行覆盖率 ≥ 70%**
- 范围建议：
  - 后端：推理适配层（请求构造/响应解析/异常分支）、任务状态机、URL 输出与静态落盘逻辑
  - 前端：URL 处理、关键页面状态切换、错误展示与重试逻辑（以组件/函数为粒度）

### 7.2 集成测试（Integration Test）

- 覆盖率要求：**关键接口路径覆盖 ≥ 50%**
- 必测链路：
  - 上传 → 创建任务 → 查询任务 → 获取可访问结果 URL
  - CORS 配置正确，前端可跨域访问后端
  - 第三方推理失败/超时的错误结构化返回

### 7.3 性能测试（Performance Test）

- 覆盖率要求：**至少覆盖 3 类场景**
  1. 低并发基线
  2. 峰值并发（模拟活动流量）
  3. 故障注入（第三方超时/失败/限流）
- 指标建议：
  - 非推理 API：p95 < 300ms（视部署环境可调整）
  - 任务创建成功率 ≥ 99%
  - 推理失败率可观测并有降级策略（见第 8 节）

### 7.4 发布门禁（Release Gate）

- CI 必须通过：lint + tests + build
- 关键路径变更必须同步更新回归用例与回归样本集

## 8. 风险应对预案

### 8.1 第三方推理不稳定/配额不足

- 预案：熔断与降级（提示排队/稍后重试/返回占位结果）
- 预案：多 Provider 策略（Gemini/自建推理/开源模型可切换）
- 预案：配额与失败率告警，提前扩容与限流

### 8.2 数据与隐私合规

- 预案：密钥不入库；不在前端/日志中输出敏感信息
- 预案：用户上传图片设置 TTL 与删除机制
- 预案：最小权限访问对象存储与第三方 API

### 8.3 成本失控

- 预案：按用户/按日限额；按任务类型设置不同超时与质量档位
- 预案：失败不无限重试；对大图进行压缩/限制尺寸

### 8.4 发布与部署失败（产物过大/缓存误上传）

- 预案：明确忽略 `.next/`、`node_modules/`、虚拟环境与缓存目录
- 预案：CI 在干净环境构建，避免携带本地缓存
- 预案：部署前进行产物体积阈值检查

### 8.5 回归质量下降（提示词或模型变更引入）

- 预案：固定回归集 + A/B；质量评分指标化；人工抽检
- 预案：提示词与配置版本化，可回滚到上一稳定版本

## 9. 交付验收标准

### 9.1 功能验收

- 完整链路可用：上传照片 → 生成数字人 → 选择姿态 → 选择单品 → 一键试穿出图
- 失败可解释：超时/配额/第三方错误都有明确提示与可重试入口
- 结果可访问：生成图片具备可访问 URL（或按设计具备鉴权访问）

### 9.2 技术验收

- 环境变量清单完整（Key 不入库），部署文档可复现
- 覆盖率达标并提供报告（单元/集成/性能）
- 监控与告警可用（至少覆盖可用性与失败率）

### 9.3 运维验收

- 具备回滚能力（回滚到上一版本可在流程内完成）
- 具备密钥轮换方案与演练记录

### 9.4 文档验收

- PRD、技术架构、API 文档、部署手册、测试用例、验收清单齐备并可交接
